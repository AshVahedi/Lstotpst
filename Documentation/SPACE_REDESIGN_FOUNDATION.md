## Coordinates and automatic progression

The gameplay plane is XY, forward is **+Y**, lateral construction is X, and camera
looks along +Z from negative Z. No steering/input controller is added. The legacy
model's `PositionX` name is retained as a scalar route-distance compatibility
detail; a presentation projection maps that scalar to Y in the space scene. All
ship, enemy and shot adapters use the same origin/orientation. Legacy defaults
remain +X. The existing route still slows during encounters and stops for the
boss/outcomes; Task 1 does not change combat pacing or enemy AI.

## Ship layout and persistence

The hull is the mandatory construction origin, not a new owned item. Four layout
mounts reference the existing persistent slot IDs:

| Slot | Side / step | Default owned item |
| --- | --- | --- |
| primary | left / 1 | basic-cannon |
| secondary | right / 1 | missile-launcher |
| defense | left / 2 | armor-plating |
| utility | right / 2 | reactor-booster |

Layout is configuration, not saved player state. Existing schema-v2 owned IDs and
installations remain authoritative; v1 migration remains unchanged. Removing an
optional item hides its module without deleting ownership. Unknown/corrupt gear
continues through the existing blocking/recovery UI and is never silently fixed.
The immutable run/profile rules still reject mid-run equipment changes.

Core width 1, bay width 0.9 and gap 0.15 give mount centers +/-1.1 and +/-2.15,
and a fully occupied width of 5.2 world units. Cells are keyed by side/positive
step; duplicate cells/IDs, unknown/unmapped equipment slots, invalid/nonfinite
geometry and excessive width are rejected. Occupancy is resolved independently
of input ordering. Structural rails connect the hull to the outermost occupied
bay, so an empty inner optional bay does not invalidate an otherwise valid old
loadout. Rails may run behind modules; module footprints never overlap.

Symmetric/asymmetric arrangements and two expansion steps per side are supported.
The origin remains at the hull even for asymmetric layouts. Bounds expose both
actual width and maximum distance from the hull: half the actual width alone is
not a safe framing measure for an asymmetric ship.

## Portrait framing

The reference is portrait 540x960 (aspect 9/16), not a pixel-to-world scale. The
camera follows the hull with zero forward lead and a minimum orthographic half
height of 8 world units. A fixed configured ship-width limit of 5.5 plus 1.5 units
of threat margin per side determines a minimum horizontal span; narrower actual
viewports increase half height according to that explicit rule. Equipping an
item does not trigger arbitrary zoom changes. At 9/16, the default horizontal
span is 9 world units, comfortably containing the 5.2-unit default ship.

The existing HUD still reserves top/bottom screen space. Incoming front enemies
may start behind its upper area or outside view, as with legacy arrivals; complete
multidirectional threat presentation and HUD redesign are later tasks. The
runtime camera is configured in the generated scene, independently of Scene view
navigation. Editor Game view must still be set to 540x960 for manual checking.

## Explicit boundaries and Task 2 handoff

Task 1 adds no new weapon channel, independent cooldown system, firing arc
calculation, steering, Energy replacement, enemy AI, sector/exploration system or
save schema. Existing combat remains a 1D front encounter projected onto +Y;
weapon shots still originate from the logical hull center rather than individual
mounts. This is an intentional temporary adapter, not completed 2D combat.

Task 2 can use stable slot IDs and mount transforms, validated layout/bounds,
positive-Y projection, the framed ship/camera, and existing immutable equipment
snapshots to introduce 2D targets/arcs and per-weapon behavior deliberately. It
must preserve the legacy orientation defaults and persistence transaction owner.

## Opening and regenerating

Open `Assets/SpacePrototypeGenerated/Scenes/SpaceFoundation.unity` alone with
Unity 6000.6.7f1, select a fixed 540x960 Game view and press Play / START LEVEL 1.
The retained Level 1 label/reward refers to the temporary combat harness, not a
new sector or a new save entitlement. UPGRADES and LOADOUT use the same profile
as the legacy scene; optional gear changes are real persistent transactions.

The menu entry is **Last Outpost > Generate Space Foundation**. It uses the same
saved-scene/dirty-target consent, owned-output cleanup and scene replacement Undo
workflow as the legacy generator. Save Untitled work manually first. Space output
is rejected inside the legacy generated folder, including case/path aliases.
Regeneration preserves the space settings asset and unrelated scene roots.

The batch entry is `LastOutpost.Editor.SpaceSceneBuilder.GenerateBatch` and has
the same saved-workspace precondition. The recorded CLI workflow used a verified
disposable project and a local batch driver that opened the existing saved
legacy scene as its workspace before invoking the safe generator. It did not
relax the preflight or save/close user work. The resulting new space tree was
copied back only after generation and validation; the legacy tree was hash-checked.
